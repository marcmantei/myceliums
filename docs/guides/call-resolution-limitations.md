# Call Resolution: Understanding Limitations and Confidence\n\n## How Call Resolution Works\n\nMyceliums builds a call graph by parsing function definitions and tracking function calls. The resolver matches call sites to their target functions using a **name-based heuristic approach**.\n\n### The Approach: Name-Based Matching\n\nThe call resolver uses this strategy, in order of precedence:\n\n1. **Expression chain resolution**: For calls like `foo.bar()`, extract the receiver type and look for `foo.bar` (qualified name)\n2. **Import aliases**: If `bar` was imported as a local alias, resolve via the import mapping\n3. **SSA-derived aliases**: If static single assignment analysis tracked `handler = authenticate`, resolve via that alias\n4. **Bare name lookup**: Fall back to matching the bare function name globally\n\n### The Limitation: Last-Writer-Wins on Common Names\n\nBecause Myceliums uses a global `name -> uid` map, **same-named symbols merge into a single entry**. This causes false positives on common names:\n\n**Example:**\n\n```rust\n// File: src/auth.rs\nfn parse(input: &str) -> Result<Token> { /* ... */ }\n\n// File: src/config.rs\nfn parse(json: &str) -> Result<Config> { /* ... */ }\n\n// File: main.rs\nlet token = parse(user_input);  // Which parse() is this?\n```\n\nBoth `parse` functions collide in the global map. The resolver cannot distinguish whether `main.rs` is calling `auth::parse` or `config::parse`, so it picks one arbitrarily (typically the last one registered). This produces a false edge in the call graph.\n\n**Real-world impact:**\n\n- A developer edited a `.tsx` file containing a `.map()` call\n- Myceliums reported **407 indirectly affected Rust symbols** via `myc impact`\n- The false positive occurred because a Rust `map` constant collided with the `.map()` method\n- Cross-language matches were equally uncertain\n\n## Interpreting Results: Confidence Guidelines\n\nWhen using `myc impact` or querying the call graph, apply these heuristics:\n\n### High Confidence (Usually Correct)\n\n- Qualified calls (`receiver.method()`): The expression chain provides type context\n- Calls to functions with **unique names** (e.g., `initializeAuthenticationSystem`)\n- Calls within the same file or module: Scoping reduces collision risk\n- Cross-language CALLS edges: A TypeScript file cannot actually call a Rust function\n\n### Low Confidence (Verify Manually)\n\n- Calls to functions with **common names** (`parse`, `handle`, `process`, `validate`, `map`, `filter`, `transform`)\n- Calls across language boundaries (e.g., TypeScript → Rust in a monorepo)\n- Impact analysis that reports **very large blast radius** (400+ affected symbols) — this is often a cascade of false positives\n- Bare-name calls where the resolver fell back to global lookup (i.e., import aliases and SSA analysis didn't apply)\n\n## De-Ranking Cross-Language Matches\n\nMyceliums automatically **de-ranks** CALLS edges that cross language boundaries. For example:\n\n- TypeScript → Rust calls are scored lower (less likely to be real)\n- Python → Java calls are scored lower\n- Results from `myc impact` deprioritize cross-language affected symbols\n\nThis is a heuristic: monorepos and polyglot systems do have cross-language dependencies, but they are rare in call graphs (more common in configuration and module imports).\n\n## Recommended Practices\n\n1. **Verify impact analysis on common-name edits**: If `myc impact` reports hundreds of affected symbols after editing a function named `handle` or `process`, spot-check the results manually. The report likely contains false positives.\n\n2. **Use unique naming**: Encourage team conventions that avoid highly generic names. `validateUserEmail` is better than `validate`.\n\n3. **Trust the call graph for exploration, verify for decisions**: The call graph is excellent for code navigation and understanding architecture, but for critical decisions (\"is it safe to refactor this?\"), combine it with your IDE's refactoring tools and test coverage analysis.\n\n4. **Rely on context queries**: Queries like `MATCH (s)-[:CALLS]->(t) WHERE s.language = 'Rust' AND t.language = 'Rust' RETURN …` automatically filter out cross-language false positives.\n\n5. **Use BM25 search for high-confidence lookups**: Text search by function name is more reliable than call graph traversal for common names.\n\n## Future Work: Precision Track\n\nThese limitations are acknowledged and planned for future versions:\n\n- **Per-file/scope keying**: Same-named symbols within different scopes become separate entries\n- **Type inference**: Build receiver types to resolve method calls exactly (e.g., `foo.bar()` becomes `TypeOfFoo.bar`)\n- **Confidence scores**: Tag each CALLS edge with a confidence percentile\n- **LSP enrichment**: Optional language-server integration for 100% precise resolution\n\nFor now, treat Myceliums as a **high-fidelity heuristic tool** — excellent for understanding code structure and identifying likely relationships, but not a replacement for static analysis tools (like `rust-analyzer`) or full-program analysis.\n"}
